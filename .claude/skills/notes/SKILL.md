# Notes 機制（開發衍生知識筆記）

> 白話：**notes ＝ 開發過程「因討論而延伸學到、但跟專案本身較無關」的
> 知識捕獲緩衝區**。它不是專案文件（那是「怎麼用這專案」），也不是
> 待辦工作（那是「要做什麼」）。它是「值不值得記住的理解」，先扁平
> 收進來，日後整包或單篇搬進你的個人知識庫（Obsidian 等）永久歸檔。
> 機制（skill）與資料（`_notes/`）分離；資料夾以 `_` 前綴排除於版控
> （理由見「資料與位置」）。

這個 skill 同時是「機制規格」與「協作協定」，是多 agent 行為的**單一
真相來源**。它管理的資料是**當前專案**根目錄下的 `_notes/`；skill 本身
（這個資料夾）無狀態，只是邏輯與規格。

## 資料與位置

- **skill 本身**（`<專案>/.claude/skills/notes/`，含 `SKILL.md`、
  `assets/`）**隨 repo commit**，走 `.gitignore` 白名單
  （`.claude/*` 排除、`!.claude/skills/` 放行），團隊共用同一份。
- **資料**在 `<專案>/_notes/`：一主題一檔 `<topic>-<subtopic>.md`
  + `INDEX.md`（人工索引）。
- **設計決策（勿違反、勿「順手修掉」）**：`_notes/` 刻意以底線開頭，
  被 `.gitignore` 的 `_*` 排除 → **每位開發者的本地知識，不進 git**。
  理由：這是個人因專案延伸的學習，不是專案產出；混進版控只會無謂衝突、
  也污染專案內容。**不要把 `_notes/` 改成被 commit**；skill 是共用的、
  notes 資料是個人的，兩者分開是刻意的。
- 「專案根」解析：從 cwd 往上找到含 `_notes/` 的祖先即專案根；首次
  （`_notes/` 尚不存在）找不到時用當前專案根，並走下方 bootstrap 的
  確認步驟。一律從專案根操作；資料位置與 skill 安裝位置無關。
  （本機制無 script，由 agent 依此規則手動定位即可，刻意不引入環境
  變數覆寫等額外機制——保持輕量。）

## 邊界：什麼進、什麼不進（最重要——避免投錯）

notes 只收**非行動的理解／知識**（判準「值不值得記住」；終點：讀懂、
搬進個人知識庫；不進版控，理由見「資料與位置」）。**不該進來的，
及其去向**：

- 「要做的事」（可行動的工作，判準「要不要做」）→ 交給**該專案的
  工作追蹤機制**（本專案目前為 backlog skill；若無則該專案慣用的
  待辦／Issue 管道）。notes 不記載、不依賴該機制的細節。
- 「用本專案的人該知道的」→ 寫進**專案文件**（readme 等，隨 repo 發佈）。

判斷流程：先問「是要做的工作嗎」→ 是則出（工作追蹤）；再問「是本專案
使用者該知道的嗎」→ 是則出（專案文件）；皆否、是因討論延伸學到、與
專案本身較無關的知識 → **收進 notes**。拿不準偏向先收進 notes（緩衝區
門檻最低，不代表承諾）。

## 首次使用（bootstrap，團隊成員無需手動建任何檔）

任何整理動作前，若 `_notes/` 不存在則自動建立，並把本 skill
`assets/INDEX.template.md` **逐字**複製成 `_notes/INDEX.md`
（冪等，絕不覆蓋既有檔）。

**第一次建立時 agent 必做**：把建立的 `_notes/` **絕對路徑**出示給
使用者，確認是否為預期專案根（agent 經非互動 shell，不做阻塞輸入；
僅出示＋說明）。若位置錯（例如不小心在子目錄），刪除該 `_notes/`、
改以正確專案根重做。已存在則不再提示（冪等、不吵）。

## 檔案規格（單一真相來源，多 agent 逐字遵守）

### 檔名

`<topic>-<subtopic>.md`。`topic` 前綴用小寫、ASCII 為主以利排序與跨平台
（如 `linux-`、`macos-`、`unix-`）；描述部分可用中文（沿用既有風格，
如 `linux-容器底層.md`）。一檔一主幹主題（綜述／連結型筆記為明示
例外，見 body 規格）；同主題多切面可多檔，靠 `topic` 歸群。

### frontmatter（平鋪 `key: value`，順序固定如下，值可空）

```
title    人類可讀標題（同時是 body 的 H1）
topic    單一主幹主題（用於 INDEX 分組），如 linux / macos / unix / git …
tags     跨領域副題清單，逗號分隔；多主題筆記靠這個表達（資料夾表達不了）
created  YYYY-MM-DD
source   緣起：哪次討論／關聯的工作項目／情境一句話。純 provenance，
         **不是硬依賴**——拿掉它筆記仍須能獨立讀懂
```

使用者/agent 手加的自訂鍵保留，不靜默丟失。

### body

自由散文。建議起首 `# <title>`，其後結構不拘（既有筆記的
「表格＋白話＋對本專案的關聯」風格是好範本，但非強制）。

- **連結在「寫的當下」就建，不事後補**：寫一篇時，凡提到已有筆記涵蓋
  的概念，當場用裸檔名連過去。互連是這套筆記的價值本體（Memex 式關聯
  網），事後補連結成本高且易漏。
- **允許「綜述／連結型筆記」**：一篇可以本身不講單一概念，而是把多篇
  串成一條脈絡／對照（如把各底層主題串起來的「總綱」式筆記）。歸在
  最相關的 `topic`，跨領域性靠 `tags` 表達。

### 可攜性規格（呼應核心需求，硬規則）

筆記必須**自足**，使任一篇或整個 `_notes/` 都能乾淨搬進個人知識庫：

1. **跨筆記連結只用裸檔名**（`[x](unix-源流.md)`），不用絕對路徑、不用
   `_notes/` 前綴 → 整夾搬走連結不斷。
2. **body 不夾專案內部流程細節**（不寫專案內部追蹤編號／狀態、不寫
   repo 路徑設定步驟）。「為什麼學這個」這類緣起放 `source` frontmatter 一句話，
   不寫進正文當依賴。
3. 內容是「可獨立成立的知識」，不是「本專案操作說明」（後者屬專案文件）。
4. **frontmatter 鍵保持一致**：`title/topic/tags/created/source`
   固定鍵名與格式不隨意增刪。搬進個人知識庫（Obsidian 等）後，一致的
   frontmatter 能被 Dataview／圖譜直接索引利用 —— 是「方便搬移保存」的
   直接回報。

> 取捨理由：捕獲階段多主題混在一夾是**正常且刻意**的——不該在討論當下
> 被迫決定知識最終歸屬。自足 + 裸連結讓「搬出去再依 topic 重組」零摩擦。
> 又：`_notes/` 刻意不版控（無 git 史），`source`/`created` frontmatter
> 是**唯一** provenance，更不可省。

## INDEX.md 人工索引（輕量，無 script）

`_notes/INDEX.md` 由 agent **每次增/改/刪筆記時手動同步**。輕量機制刻意
不上 script/自動編號/封存；但為多 agent 一致，格式定死如下：

- 開頭一段：本夾用途一句話（從模板來，可手寫微調，agent 勿亂改）。
- `## <topic>` 一個主題一節（依 topic 字母序），節內逐筆：
  `- [<title>](<檔名>.md) — <一句話鉤子>` ；該筆有 `tags` 則接
  ` · tags: a, b`。
- 同一篇若跨多主題：歸在其 `topic` 節，跨領域性靠該行 `tags:` 呈現，
  **不重複列在多節**（避免索引膨脹與不一致）。
- 結尾一行：`_最後更新：YYYY-MM-DD_`。

### INDEX 是召回入口（agent 行為——最重要）

INDEX 不只是「給人看的目錄」，更是 **agent 回找知識的入口**。當需要
取用 `_notes/` 既有知識時，**先讀 `INDEX.md` 依 topic／鉤子／tags 定位
候選，再開那一篇細讀**，不要盲目全夾掃讀。這讓筆記在數量長大後仍能被
精準回找（取代 RAG 的輕量做法）。因此「鉤子一句話寫得準」不是美觀問題，
而是召回品質本身 —— 寫索引行時就當它是日後檢索的關鍵字。

## 多主題與階層

- **資料夾名去主題化**：`_notes/` 是通用容器，不以任何單一主題命名
  （它天生多主題）。主題只活在 frontmatter `topic`/`tags` 與 INDEX 分組。
- **用 metadata 表達層級，不用子資料夾**：知識常跨主題（一篇可同時涉
  linux 與 macos），子資料夾強迫單一父歸屬會逼亂塞；`tags` 能表達「屬
  多主題」，資料夾不能。預設**扁平**。
- **拆分啟發式**：當某個概念被多篇反覆提及、卻沒有自己的
  一篇 → 把它抽出獨立成篇，讓相關各篇回連過去。判準是「被引用的頻度
  與份量」，不是預先規劃。
- **逃生口（需明確理由才啟用）**：當某 `topic` 累積到夠大、自成體系，
  *可*把該主題筆記升級進 `_notes/<topic>/` 子資料夾，並讓該子夾成為
  「整包搬進個人知識庫」的乾淨單位。預設不做；要做時 agent 須說明理由、
  由使用者點頭，並同步 INDEX 與裸連結（仍以檔名互連）。

## 協作協定（給 agent 的行為準則）

- **觸發**：預設「使用者明講要記」。離題知識在討論中長大時，agent *可*
  **主動建議**「要不要把這段收進 `_notes/`？」，但**未經同意不自動寫**。
- **知識複利**：討論過程中產生的有價值分析／對照／推導
  **不是用完即丟的對話**——值得保留的就主動提議沉澱成筆記。這套筆記的
  價值來自「答案不蒸發、持續累積且互連」，正是本 skill 的核心情境。
- **落筆前確認知識點已成形**：寫一篇前，先與使用者確認「該知識點已
  討論到一個**完整段落**、不是討論中途的半成品」，得到點頭才落筆。
  寧可等討論收斂再記，避免把仍在演進的內容過早凍結成筆記（之後還要
  回頭大改，反而違背輕量與知識複利）。與「未經同意不自動寫」一致：
  同意「要記」之外，還要確認「現在記時機對」。
- **矛盾要標出，不默默覆蓋**：新知識與既有筆記衝突時，
  **明確指出矛盾點、列出雙方說法，交使用者裁決**；不靜默改寫舊筆記、
  也不無聲並存兩個互斥版本。修正後在該筆記註明「修正自／取代舊說」。
- **三道關卡（投哪／升不升／不收）**：
  - *收進 notes*：因討論延伸、與專案本身較無關、值得日後回看的理解。
    粗略也行，緩衝區門檻最低，拿不準先收。
  - *不收*：(a) 屬「要做的工作」→ 交給該專案的工作追蹤機制（本專案
    為 backlog skill）；(b) 屬「用本專案的人該知道的」→ 寫進專案文件；
    (c) 一次性瑣碎、查完即丟、無保留價值 → 不記。
  - *合併不重開*：新知識與既有某篇是同一主題的延伸 → 併進該篇或新增同
    `topic` 檔並在 INDEX 同節並列，不無謂碎片化。
- **一次一篇（WIP=1）**：使用者要整理某段討論 → 聚焦那一篇，寫好、更新
  INDEX，不批次替使用者決定多篇結構。
- **不污染專案**：本 skill 只操作 `_notes/`；這類知識**絕不**寫進
  `readme.md` 等專案文件，也不動使用者其他個人檔，除非使用者明確要求。
- **結構性決定**（命名、是否升子夾、是否合併）要明講理由並標示可否決，
  不默默決定。
- **既有同性質舊資料**：若專案內另有同性質的舊筆記夾，**agent 不自動
  搬遷/改名/合併/刪除**（屬重構，WIP=1、不默默動）；可向使用者*建議*
  併入本標準，由使用者裁示後才動，且預設保留原夾不刪。

## 健檢／整理（使用者觸發，無自動化）

對應 skill 描述的「整理既有筆記」觸發。**僅在使用者明講時執行**，無
排程、無 script —— 保持輕量。一次健檢，agent 掃過 `_notes/` 處理下列
項，處置分兩級：**第 0 項是純記帳，直接修好並告知**；**第 1–5 項涉及
知識判斷，只報告＋建議，實際變更 WIP=1、逐項由使用者點頭**。

0. **INDEX 對帳／重建**（最基礎，直接修）：掃 `_notes/*.md` 實際檔案
   對照 `INDEX.md` —— 補上漏列的、刪掉指向不存在檔的死列、刷新過期的
   鉤子／tags、修正 topic 分組與字母序、更新「最後更新」日期。INDEX 是
   召回入口，錯了回找就錯；這本是每次增／刪筆記就該同步、健檢時補做的
   記帳，非知識判斷，故直接校正到與實際一致，不必逐行等點頭（修完告知
   差異即可）。
1. **矛盾**：彼此說法衝突的筆記（同「矛盾要標出」原則，但這裡是回頭批次掃）。
2. **過時**：被後來的認知推翻／取代的論點。
3. **孤立**：沒有任何入連或出連的筆記（可能漏建關聯，或該併入他篇）。
4. **缺失互連**：明顯相關卻沒互連的筆記對。
5. **缺口與後續**：值得補但還沒記的主題、值得再深究的問題。

第 1–5 項只「找出＋建議」，不批次自動改；逐項修整時回到「一次一篇」節奏。

## 已知假設與限制（刻意取捨，非 bug）

- **INDEX 人工維護**：無 script 重生，靠 agent 每次增／刪筆記時同步。
  多 agent 高並發編輯仍可能漂移；輕量機制接受此風險（知識筆記非高頻
  並發狀態機），並以「健檢第 0 項：INDEX 對帳／重建」為校正手段。
- **無 id／無封存／無自動排序**：刻意——散文知識不需工作項目那套生命週期。
  需要那套生命週期的是「工作」，交給該專案的工作追蹤機制（如 backlog skill）。
- **SKILL.md 是規格與文字的真相來源**；`assets/INDEX.template.md` 只是
  bootstrap 種子，兩者若漂移以 SKILL.md 為準。

## 版本與同步

本 skill 目前以「逐 repo 複製檔案」方式跨專案同步。為避免「誰是最新」
漂移：

- frontmatter 維持 `version` + `updated` 兩欄
  - `version`：語意化版號（bug 修補 patch、新增小功能 minor、breaking 改 major）
  - `updated`：YYYY-MM-DD，最近一次內容變動日期
- **修改本檔或 `assets/` 前**先 bump `version` 並更新 `updated`。跨 repo
  同步比對時版號高者為準。

> 中長期規劃：抽出獨立 skill 維護 repo（git submodule 引入各專案），
> 屆時版號比對改為「對齊該 repo 某個 release」。
